# Exploration and selection

Read when the deliverable is visual alternatives, a mockup, a design choice, or a combination of options.

## Compare useful alternatives

Use the supplied audience, task, brand assets, content, and technical constraints. Inspect the relevant surface or references first. If a fact is discoverable, find it; ask only when a missing product decision prevents a useful comparison. Exploration itself is a valid deliverable while visual direction is open.

Produce the requested number of options. Keep content, representative data, viewport, and task comparable. Vary information hierarchy, composition, density, navigation, or interaction rather than merely changing accent colors. Explain each concept's useful tradeoff briefly. Mark synthetic data and unimplemented metrics where they might be mistaken for existing capabilities. A mockup must not invent a business rule to make its dashboard look populated.

Use the runtime's supported inline rendering or a lightweight local viewer. Inspect the rendered options for clipping, legibility, main-action visibility, and relevant narrow-screen or interaction states. A static layout does not prove functional behavior. Keep exploratory files isolated from the working application unless the user asks otherwise; production builds, translations, deployment infrastructure, and application test suites are unnecessary for a standalone mockup.

Done: each requested option is viewable, meaningfully different, and comparable against the same task. Give a recommendation and its reason without selecting on the user's behalf.

## Keep the selection exact

Assign stable IDs and distinctive names within a round, such as `R1-E / Focus Hero`. Keep them attached to each rendered artifact. New rounds get new IDs; preserve older artifacts that are still referenced.

Record the selected ID/name, artifact path or attachment, requested combinations, retained behavior, and superseded choices in existing task state. For a short task, a concise conversation note is enough; use the repository's decision convention for sustained work. Pass that selection to workers and handoffs. “Focus” matching both Focus Hero and Focus Deck needs one short clarification before application implementation. An unambiguous selection can proceed within existing authorization.

When combining options, render the combination if requested before implementing it. Build the approved composition; surface material accessibility, responsive, data, or feasibility adaptations rather than silently substituting another concept.

Done: the implemented surface can be compared directly with the selected artifact, and every deliberate material departure has a reason visible to the user.
