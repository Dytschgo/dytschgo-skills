# Astra Triage

Move issues through a small state machine of triage roles. Behavior follows Matt Pocock's triage skill (MIT): https://github.com/mattpocock/skills/blob/v1.3.1/skills/engineering/triage/SKILL.md

If this repo treats external pull requests as a request surface, triage covers them too. A PR is an issue with attached code: same roles, same states, same machine, with the deltas marked below. Resolve a bare `#42` to an issue or a PR the way this repo's tracker does.

Every comment or issue this skill posts starts with:

```markdown
> *This was generated by AI during triage.*
```

## Roles

Two category roles: `bug` (something is broken) and `enhancement` (a new feature or improvement).

Five state roles:

- `needs-triage`: a maintainer still has to evaluate it.
- `needs-info`: waiting on the reporter.
- `ready-for-agent`: fully specified, ready for an agent that can run unattended.
- `ready-for-human`: needs a person to implement, or, for a PR, a person to merge.
- `wontfix`: will not be actioned.

For a PR, read the same states against the attached code. `ready-for-agent` means a brief is attached and an agent should take the next step on the diff. `ready-for-human` means a person should merge it.

Every triaged item carries exactly one category role and one state role. If state roles conflict, flag that and ask the maintainer before doing anything else.

These names are canonical. The tracker's label strings may differ. Use the map the repo already documents. If it documents none, use these names as the labels and say that you did.

An unlabeled item normally goes to `needs-triage` first, then to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override. Flag a transition that looks unusual and ask before proceeding.

## Show what needs attention

When the maintainer asks what needs them, query the tracker and present three buckets, oldest first:

1. Unlabeled. Never triaged.
2. `needs-triage`. Evaluation in progress.
3. `needs-info` where the reporter has written since the last triage notes.

When PRs are in scope, include external PRs and tag each line `[PR]` or `[issue]`. Discovery lists only external PRs, using whoever this repo counts as external, so a collaborator's in-flight PR is not triage work. That filter is for discovery only. An explicitly named PR is triaged whoever wrote it.

Show counts and a one-line summary. Let the maintainer pick.

## Triage one issue or PR

1. **Gather context.** Read the full item: body, comments, labels, author, dates, and for a PR the diff. Parse earlier triage notes so you do not re-ask a settled question. Explore the codebase in its glossary, respecting ADRs in the area. Then two checks. Redundancy: search for an existing implementation of the requested behavior by domain concept, not just the wording, and report where you looked. If you find it, this is an already-implemented `wontfix`. Prior rejection: read `.out-of-scope/*.md` and surface any file that resembles this request.

2. **Recommend.** Tell the maintainer the category and state you recommend, why, and a short codebase summary, including whether it is already implemented. Wait for direction.

3. **Verify before any grilling.** A bug: reproduce it from the reporter's steps. A PR: confirm the diff does what it claims. Check it out and run the relevant tests or commands. Report confirmed (with the code path), failed, or insufficient detail. Insufficient detail is a strong `needs-info` signal. Do not pull [Astra Grilling](../astra-grilling/SKILL.md) until this step has a result.

4. **Grill only if the request still needs fleshing out.** Pull [Astra Grilling](../astra-grilling/SKILL.md) and interview one frontier round at a time. Where the repo has a glossary or ADRs, use those terms and update them when a decision changes a term. Do not grill a claim you have not tried to reproduce.

5. **Apply the outcome.**
   - `ready-for-agent`: post an agent brief, using the template below.
   - `ready-for-human`: the same shape, plus why it cannot be delegated (judgement, external access, a design decision, or manual testing).
   - `needs-info`: post triage notes from the template below.
   - `wontfix`: close it. The comment depends on why. Already implemented: point at where it lives, and do not write `.out-of-scope/` (that directory is for rejected requests, not shipped ones). Rejected bug: a polite explanation, then close. Rejected enhancement: write or update `.out-of-scope/`, link it from the comment, then close.
   - `needs-triage`: apply the role. Comment only if there is partial progress worth keeping.

## Quick override

If the maintainer says "move #42 to ready-for-agent", trust them. Confirm the role change, the comment, and any close, then act. Skip grilling. If they move it to `ready-for-agent` without a grilling session, ask whether they want an agent brief.

## Needs-info notes

```markdown
## Triage Notes

**What we've established so far:**

- point

**What we still need from you (@reporter):**

- a specific question, not "please provide more info"
```

Put everything grilling already resolved under "established so far" so that work is not lost.

## Agent brief

The brief is the contract an unattended agent will work from. The original body is context. Write what the agent should do. On an issue, that is building the change. On a PR, that is what remains to do to the existing diff.

Write for durability. The item may sit for weeks while files move. Describe interfaces, types, and behavioral contracts. Name types, signatures, or config shapes the agent should look for. Do not cite file paths or line numbers, and do not assume today's structure will hold.

Describe what the system should do, not the procedure. The agent explores fresh.

Every brief has acceptance criteria a stranger can check, and an explicit out of scope, so the agent does not gold-plate.

```markdown
## Agent Brief

**Category:** bug or enhancement
**Summary:** one line

**Current behavior:**
What happens now. For a bug, the broken behavior. For a PR, the state of the diff, including gaps.

**Desired behavior:**
What should be true when the work is done, including edge and error cases.

**Key interfaces:**
- Types, function contracts, or config shapes that must change, and why.

**Acceptance criteria:**
- [ ] A specific check
- [ ] A specific check

**Out of scope:**
- What this item must not take on
```

## Out of scope files

`.out-of-scope/` remembers rejected enhancements so the next similar request does not relitigate them. One file per concept, not per issue. Name it in kebab-case for the concept, for example `dark-mode.md`.

```markdown
# Concept name

## Why this is out of scope

A durable reason: project scope, a technical constraint, or a strategic choice. Not "we are busy", which is a deferral.

## Prior requests

- #42: short title
```

During gather-context, read the directory. Match by concept, not keyword. If one resembles the new request, tell the maintainer and quote the reason. If they confirm, append the new issue under Prior requests and close. Do not reopen a rejection from this skill.

## Resume

If triage notes already exist, read them, check whether the reporter answered, and present the updated picture before continuing. Do not re-ask a resolved question.

## Hand off

A brief marked `ready-for-agent` can be split with [Astra To Tickets](../astra-to-tickets/SKILL.md) or built with [Astra Engineering](../astra-engineering/SKILL.md). Grilling a bug report that has not been through step 3 is out of order. Pull this skill first.
